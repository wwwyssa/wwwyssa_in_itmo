# Backend API

Базовый путь — `/api`, например `http://localhost:8080/api`. Фактический внешний порт Docker задаёт `BACKEND_PORT` в `.env`.

Пользовательский интерфейс открывается на `/` того же сервера, например `http://localhost:8081/` при `BACKEND_PORT=8081`. Статические HTML/CSS и модули JavaScript поставляются внутри WAR. Они обращаются к `/api` на том же адресе. При пересборке обновляются и backend, и интерфейс.

Меню содержит квартиры, дома, координаты и специальные операции. Заголовки колонок переключают сортировку, фильтры применяются кнопкой «Найти», а «Сбросить» очищает их. Формы открываются в диалогах; существующие связанные объекты выбираются из постраничного списка, новые можно создавать из окна выбора. Все поля квартиры и связанных объектов доступны в таблице с горизонтальной прокруткой и в отдельном просмотре. Открытый список автоматически обновляется после уведомления WebSocket; кнопка «Обновить» также доступна.

## Запуск

Нужны Java 17 для локальной сборки либо Docker для полного запуска. Создайте `.env` из `.env.example` и задайте пароль БД.

`JWT_SECRET` задаёт ключ подписи: Base64 от минимум 32 случайных байтов. Если оставить значение пустым, приложение генерирует ключ при запуске; после перезапуска ранее выданные токены становятся недействительными. Чтобы сохранить вход после перезапуска, сгенерируйте постоянный ключ и внесите его в `.env`:

```powershell
$jwtBytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($jwtBytes)
[Convert]::ToBase64String($jwtBytes)
```

Для новой базы:

```powershell
docker compose up -d --build
```

Для существующей базы, в которой уже применена схема `schema.sql`:

```powershell
docker compose up -d db
Get-Content -Raw db/init/flat_functions.sql | docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
Get-Content -Raw db/init/users.sql | docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose up -d --build backend
```

Init-скрипты PostgreSQL выполняются только при создании базы, поэтому для существующего volume функции применяются отдельно. Данные при этом сохраняются.

Для локального WildFly соберите и скопируйте WAR командой `.\backend\deploy-local.ps1`, затем запустите `.\wildfly\bin\standalone.bat`. Локальный WildFly должен быть предварительно настроен с модулями PostgreSQL, EclipseLink и источником данных `java:/jdbc/flats`; Docker-образ выполняет эту настройку автоматически.

## Формат ответа

Успешные ответы содержат данные напрямую: объект квартиры, дома или координат, страницу списка, массив квартир либо число для операции подсчёта. Оболочки `code`, `message`, `result` нет. Статус передаётся средствами HTTP: создание возвращает `201` и заголовок `Location`; успешное чтение, изменение и удаление — `200`.

Ошибки содержат JSON-объект с полем `message`: `400` для неверных значений, `404` для отсутствующего объекта. Ошибки БД и другие непредвиденные исключения возвращают `500` с телом `{"message": "Ошибка БД"}`. Ответ формирует один простой `ErrorHandler`.

Ответ списка:

```json
{
  "items": [],
  "page": 0,
  "size": 20,
  "totalElements": 0,
  "totalPages": 0
}
```

`page` начинается с `0`, по умолчанию `0`. `size` — от `1` до `100`, по умолчанию `20`. `totalElements` и `totalPages` относятся к данным после фильтрации. Страница за пределами списка возвращает пустой `items`, сохраняя метаданные. Недопустимые параметры страницы возвращают `400`.

`sort` по умолчанию `id`, `direction` — `asc` или `desc` (по умолчанию `asc`, регистр значения не важен). При равенстве сортируемых значений используется дополнительная сортировка по ID по возрастанию. Для `NULL` используется порядок PostgreSQL: в конце при `asc`, в начале при `desc`. Границы страниц детерминированы для неизменившихся данных; список может сдвинуться после добавления или удаления записей.

Текстовые фильтры списка ищут подстроку без учёта регистра через SQL `LIKE`. В текущей реализации `%` и `_` имеют значение шаблонных символов, а обратный слеш используется для экранирования. Числовые фильтры ищут точное совпадение. Несколько фильтров соединяются через AND; отсутствующий фильтр не ограничивает список. Параметры URL нужно кодировать обычными средствами HTTP-клиента.

## Квартиры

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/flats` | Список квартир |
| GET | `/flats/{id}` | Полные сведения о квартире |
| POST | `/flats` | Создать квартиру |
| PUT | `/flats/{id}` | Полностью заменить изменяемые атрибуты |
| DELETE | `/flats/{id}` | Удалить квартиру, вернуть её прежние данные |

Фильтры списка: `name` и `houseName` — поиск подстроки; `numberOfRooms` — точное число комнат от 1 до 11; `timeToMetroOnFoot` — точное положительное конечное число. Пустые текстовые фильтры игнорируются, а нечисловые и недопустимые числовые значения возвращают `400`.

Доступные поля `sort`: `id`, `name`, `coordinatesId`, `x`, `y`, `creationDate`, `area`, `price`, `balcony`, `timeToMetroOnFoot`, `numberOfRooms`, `furniture`, `view`, `transport`, `houseId`, `houseName`, `houseYear`, `houseNumberOfFloors`.

Пример: `GET /api/flats?page=0&size=10&sort=price&direction=desc&numberOfRooms=2&timeToMetroOnFoot=5`.

Тело создания или изменения:

```json
{
  "name": "Квартира у парка",
  "coordinatesId": 1,
  "area": 60,
  "price": 12000000,
  "balcony": false,
  "timeToMetroOnFoot": 8,
  "numberOfRooms": 2,
  "furniture": null,
  "view": "PARK",
  "transport": "NORMAL",
  "houseId": 1
}
```

Вместо `coordinatesId` можно передать `x` и `y`, тогда сервер создаст новые координаты в той же транзакции. Одновременная передача ID и значений координат запрещена. `houseId` необязателен; отсутствие или `null` означает квартиру без дома. Связанные ID должны быть положительными и существовать. При неправильной ссылке создание/изменение возвращает `400`, все изменения транзакции откатываются.

`PUT` требует полного набора обязательных полей; это не частичное обновление. ID и `creationDate` формирует сервер, дата не изменяется при обновлении. Ответ содержит все поля квартиры, координат и дома в плоском DTO, в том числе `houseYear` и `houseNumberOfFloors`. Необязательные поля явно передаются как `null`.

Допустимые значения `view`: `STREET`, `YARD`, `PARK`, `BAD`, `TERRIBLE`. Значения `transport`: `FEW`, `LITTLE`, `NORMAL` или `null`. В JSON перечисления регистрозависимы. Неизвестный enum и неправильный тип поля возвращают `400`.

## Дома и координаты

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/houses` | Список домов с пагинацией, фильтром `name` и сортировкой |
| GET | `/houses/{id}` | Дом по ID |
| POST | `/houses` | Создать дом |
| GET | `/coordinates` | Список координат с пагинацией и сортировкой |
| GET | `/coordinates/{id}` | Координаты по ID |
| POST | `/coordinates` | Создать координаты |

Для домов `sort`: `id`, `name`, `year`, `numberOfFloors`. Для координат: `id`, `x`, `y`. Формат страниц и общие параметры совпадают со списком квартир.

`POST /api/houses`:

```json
{"name": "Дом у парка", "year": 2005, "numberOfFloors": 9}
```

`name` не может быть `null`; пустое имя дома разрешено формулировкой задания. `year` и `numberOfFloors` должны быть положительными. Ответ содержит `id`, `name`, `year`, `numberOfFloors`.

`POST /api/coordinates`:

```json
{"x": 12.5, "y": 249}
```

Обе координаты обязательны и должны быть конечными числами, `y <= 249`. Ответ содержит `id`, `x`, `y`. Одни координаты и один дом могут использоваться несколькими квартирами. Удаление квартиры не удаляет эти самостоятельные записи.

## Специальные операции

Все пять методов вызывают функции PostgreSQL через JPA из серверной бизнес-логики; вычисление результата выполняется в БД.

| GET-путь | Параметры | Тело ответа |
| --- | --- | --- |
| `/flats/operations/max-area` | Нет | DTO квартиры с максимальной площадью |
| `/flats/operations/count-by-house` | Необязательный `houseId` | Число квартир в этом доме |
| `/flats/operations/name-prefix` | Обязательный `prefix` | Массив DTO квартир |
| `/flats/operations/most-expensive-without-balcony` | Нет | DTO самой дорогой квартиры без балкона |
| `/flats/operations/most-expensive-of-three` | `id1`, `id2`, `id3` | DTO самой дорогой из указанных квартир |

Правила:

- При равной площади или цене выбирается квартира с меньшим ID.
- Для подсчёта отсутствие `houseId` означает квартиры без дома; положительный несуществующий ID даёт `0`.
- Префикс имени **регистрозависим и буквален**, результат упорядочен по ID. Пустой `prefix=` возвращает все квартиры, отсутствие параметра — `400`, отсутствие совпадений — пустой массив. Пагинации у этой операции нет, поскольку задание требует массив.
- «Без балкона» означает `balcony = false`. `null` означает неизвестное значение и не включается.
- Для выбора из трёх требуются три различных положительных ID: неверные аргументы дают `400`, отсутствующая квартира — `404`.
- Операции с результатом в виде одной квартиры возвращают `404`, если подходящих объектов нет.

Пример: `GET /api/flats/operations/most-expensive-of-three?id1=1&id2=2&id3=3`.

## Регистрация и вход

Интерфейс открывает экран входа с переключателем регистрации. Форма ограничивает логин 3–32 латинскими буквами, цифрами или символами `_`, а пароль — 8–128 символами. Регистр логина не учитывается. После регистрации пользователь сразу входит в приложение.

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/auth/register` | `201`: JWT и данные входа; `409`, если логин занят |
| POST | `/auth/login` | `200`: JWT и данные входа; `401`, если логин или пароль неверны |

Тело обоих запросов:

```json
{"username": "user_1", "password": "my-password-123"}
```

Ответ содержит `token`, `username` и `expiresAt` (Unix-время в секундах). Подпись JWT — HS256; срок действия — один час. Пароли хранятся в `app_user` как PBKDF2-HMAC-SHA256 с индивидуальной случайной солью и 600 000 итераций.

Все остальные REST-запросы требуют заголовок `Authorization: Bearer <token>`. Без действительного токена сервер возвращает `401`. Любой вошедший пользователь может просматривать, создавать, редактировать и удалять любые квартиры. Связи квартиры с создателем и разграничения прав по владельцу нет.

Фронтенд хранит JWT в `sessionStorage` текущей вкладки и автоматически добавляет заголовок. При истечении срока действия или ответе `401` открывается экран входа. Кнопка «Выйти» удаляет токен из вкладки и закрывает WebSocket; ранее выданный JWT действует до своего срока истечения.

Для существующей БД примените `db/init/users.sql` командой из раздела «Запуск»: она создаёт таблицу пользователей и сохраняет квартиры. Для новой БД Compose применяет `users.sql` третьим init-скриптом. При обращении через HTTPS браузер использует защищённый WebSocket `wss`.

## Актуальность данных между пользователями

Клиент получает актуальные данные при следующем REST-запросе после успешного завершения изменяющей транзакции. Например, пользователь А просмотрел квартиру, пользователь Б изменил её через `PUT /api/flats/{id}`, после чего следующий `GET /api/flats/{id}` пользователя А возвращает новые значения. Повторная загрузка `GET /api/flats` учитывает изменения в списке, фильтрах и сортировке. После удаления квартиры запрос по её ID возвращает `404`.

Каждый вошедший клиент подключается к WebSocket `/updates` (относительно корня приложения) и первым текстовым сообщением передаёт JWT. После проверки сервер отвечает `ready` и включает подключение в рассылку. Недействительный токен закрывает соединение с кодом `1008`; неавторизованное соединение не получает уведомлений. Ожидание первого сообщения ограничено 10 секундами. После успешного завершения транзакции создания дома/координат или создания, изменения, удаления квартиры сервер отправляет авторизованным клиентам текст `changed`. Клиент повторно загружает открытый основной список, сохраняя фильтры, сортировку и страницу. Откатившаяся транзакция уведомление не отправляет. Перед рассылкой сервер также проверяет срок действия токена подключения.

При разрыве WebSocket клиент пробует подключиться снова через 3 секунды. При установлении соединения список также загружается, чтобы получить изменения, пропущенные во время разрыва. Диалоги просмотра, формы редактирования, выбор связанных объектов и результаты специальных операций загружаются при обращении к ним.

## Архитектура

Списки квартир, домов и координат строятся через JPA Criteria API. Для пяти специальных операций используются native queries, вызывающие функции PostgreSQL.

HTTP-контроллеры находятся в `web` и имеют суффикс `Controller`: `FlatController`, `HouseController`, `CoordinatesController`, `FlatOperationsController`. Транзакционная бизнес-логика находится в `service`, классы имеют суффикс `Service`: `FlatService`, `HouseService`, `CoordinatesService`, `FlatOperationsService`. Каждый контроллер вызывает соответствующий сервис через `@EJB`; сервисы обращаются к `FlatRepository`, `HouseRepository` и `CoordinatesRepository`. Входные и выходные объекты находятся в `dto`, ORM-сущности — в `model`. Интерфейс использует REST API; EJB-сервисы также можно вызывать напрямую из управляемых бинов.

Классы внутри `service` разделены по назначению:

| Пакет | Классы |
| --- | --- |
| `service.auth` | `AuthService`, `JwtService`, `PasswordSupport` |
| `service.flat` | `FlatService`, `FlatOperationsService`, `FlatSearch` |
| `service.house` | `HouseService` |
| `service.coordinates` | `CoordinatesService` |
| `service.pagination` | `PageRequest` |
| `service.exception` | `BadRequestException`, `NotFoundException`, `ConflictException`, `UnauthorizedException` |
| `service.notification` | `ChangeNotifier` |
